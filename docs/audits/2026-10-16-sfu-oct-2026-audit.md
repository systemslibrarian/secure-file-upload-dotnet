## Threat Model and Pipeline Mapping

### Trust Boundaries

```
ATTACKER CONTROLLED INPUT
  -> Layer 1: Size check (per-file + batch total)
  -> Layer 2: Extension allowlist (.jpg, .jpeg, .png, .webp, .pdf)
  -> Layer 3: MIME type + extension cross-validation
  -> Layer 4: Magic bytes / file signature
  -> Layer 5: Filename inspection (traversal, bidi, double-ext)
  -> Layer 6: Deep content validation (structural + pattern scanning)
  -> Layer 7: Virus scan (optional; fail-open on availability by default)
  -> Layer 8: Encrypted storage (optional by default) + path containment
  -> STORAGE: Files encrypted with AES-256-GCM (if enabled), outside wwwroot
  -> DOWNLOAD: Opaque signed tokens, path re-check, hardened headers
```

## Previous Review Adjudication

### Claim A: Static Argon2id Salt

**Status: CONFIRMED (with qualification)**

**Code Evidence:**
```csharp
// src/FileUploadService.cs lines 167-168
private static readonly byte[] Argon2idSalt = 
    Encoding.UTF8.GetBytes("SecureFileUpload.kdf.argon2id.v1");
```

**What an attacker must obtain:** EncryptionSecret only (salt is public).

**Impact Assessment:**
- Argon2id parameters (64 MiB, 3 iterations, 4 parallelism) provide strong protection
- Static salt is **not a vulnerability** - KDF strength comes from memory-hard work factor
- Real risk is weak or exposed EncryptionSecret, not the salt
- Cross-deployment KEK correlation is theoretical (each deployment should have unique secret)

**Verdict:** Salt being public is **acceptable practice** for application-level KDF. The library's startup guard blocks missing/placeholder secrets.

## New Findings Beyond Previous Review

### SFU-OCT-001: Integer Overflow in Total Upload Size Calculation (HIGH)

**Severity:** HIGH  
**Confidence:** Statically established  
**Evidence:** Source code analysis

**Location:** `src/FileUploadService.cs` lines 631, 636

**Root Cause:** `files.Sum(f => f?.Length ?? 0L)` uses unchecked arithmetic. With default config (5 files × 10 MB), overflow is impossible. However, with custom large limits, overflow could bypass the batch size check.

**Attack Path:**
1. Operator configures very large `_maxFileSizeBytes` and `_maxFileCount`
2. Attacker submits files with sizes causing `long` overflow in sum
3. Check `totalUploadBytes > _maxTotalUploadBytes` passes incorrectly

**Realistic Impact:** Low in default configuration (50 MB max batch). Theoretical with custom configuration.

**Recommended Fix:**
```csharp
long totalUploadBytes = 0;
foreach (var f in files)
{
    checked
    {
        totalUploadBytes += f?.Length ?? 0L;
    }
}
```

**Relation to Previous Review:** New finding.

## Appendix A: Pipeline Layer Details

### Encrypted File Formats

**v1 (Legacy):** `[8:marker][12:nonce][16:tag][ciphertext]` - Direct KEK encryption, decrypt-only

**v2 (Current):** `[8:marker][12:dek_nonce][16:dek_tag][32:wrapped_dek][12:file_nonce][16:file_tag][ciphertext]` - Envelope encryption with per-file DEK

### Supported File Types
- .jpg/.jpeg: JPEG segment walker, magic bytes 0xFF,0xD8,0xFF
- .png: PNG chunk walker, magic bytes 0x89,0x50,0x4E,0x47,0x0D,0x0A,0x1A,0x0A
- .webp: WebP RIFF walker, magic bytes 0x52,0x49,0x46,0x46 + "WEBP" at offset 8
- .pdf: PDF lexer + pattern scan, magic bytes 0x25,0x50,0x44,0x46

## Conclusion

The SecureFileUpload.Core library implements a sophisticated, defense-in-depth file upload pipeline that addresses nearly all common file-upload attack vectors. The code demonstrates strong cryptographic practices (Argon2id, AES-GCM, envelope encryption), proper input validation, and careful filesystem handling.

However, **seven findings** require attention:
- **1 HIGH-severity new vulnerability** (integer overflow with custom config)
- **3 HIGH/MEDIUM-severity configuration gaps** (encryption disabled, AV fail-open, token bearer by default)
- **2 MEDIUM-severity design observations** (static salt, Unicode filenames)
- **1 INFORMATIONAL refutation** (PDF streams are rejected, not skipped)

**The library's security posture is strong, but operators must understand and accept the documented trade-offs, particularly around encryption being opt-in and AV availability being fail-open by default.**

**Before production deployment:**
1. Enable encryption and configure a strong EncryptionSecret
2. Consider enabling FailClosedOnUnavailable for higher-risk contexts
3. Enable BindTokensToUser for multi-user deployments
4. Review and customize all size limits for your environment
5. Monitor ScanNotScannedCount for scanner availability issues
